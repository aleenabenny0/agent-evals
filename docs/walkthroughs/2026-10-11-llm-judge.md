# Walkthrough: the LLM judge and how it earns trust

What the judge decides, why it is kept away from the agent's run, and how its validation numbers
are computed. Plan and decisions: `docs/plans/llm-judge.md`. Written so each part can be explained
in an interview without the original conversation.

## 1. Two questions code cannot settle

The deterministic graders settle most of what matters: required phrases present, abstained when
it should, citations real and verbatim, output well formed, numbers on the pages it read. Two
things remain judgment calls:

- **Supported**: does every claim in the answer follow from the quotes it cited? The quotes are
  verified verbatim by code, but code cannot tell whether "you can retain for 35 days" follows
  from a quote about recovery periods.
- **Responsive**: does the answer answer the question that was asked? Keyword matching passes an
  answer that has the right numbers for the wrong question.

Aleena decided against a third "complete" verdict: an incomplete answer to a multi-part question
is not responsive, so it fails that verdict already.

## 2. Information hygiene

The "supported" prompt is shown the question, the answer and the cited quotes. It never sees the
gold answer, so it cannot be swayed by knowing what the right answer was; it judges only whether
the citations carry the claims. The "responsive" prompt is shown the gold answer, because
"answers the question" needs a reference. `tests/test_judge.py` pins both facts by inspecting the
requests the fake client received.

Each verdict comes back through a strict tool, `submit_verdict`, which the system prompt tells
the model to call. The verdict is a Pydantic model with a two-value enum. There is no prose
parsing, and a missing or malformed verdict becomes a `grader_error`, never a silent pass. A
forced `tool_choice` would be tidier, but claude-sonnet-5-5 rejects it with a 400; the first
judge run found that out at a cost of zero, because every attempt errored before any call.

## 3. Why the judge runs after the run

`evals run` never calls the judge. `evals judge RUN_ID` reads the stored answers and adds its two
grades beside the code graders' grades, recording the judge version, model and salt in the run
manifest. Three reasons:

- The agent run is cheap (Haiku) and the judge is not (Sonnet). Keeping them apart means a run
  can be judged, re-judged with a new prompt, or left unjudged, without re-running the agent.
- Judging old runs is how the judge gets validated and tuned: the labels are attached to stored
  answers, and the judge is scored against them.
- The judge skips what code already settled: errored attempts, abstentions, and "supported" when
  there are no citations at all (`uncited_answer` has that covered). It never overrides a code
  grade.

Every judge call goes through the same cached `LLMClient` as the agent. That means re-judging an
unchanged answer is free and reproducible, which is what you want in a report, and it means a
stability check needs a fresh cache key: `--salt probe` gives one.

## 4. Validation: three kinds of evidence

A judge number counts only after the judge has been checked against people and against planted
errors. `docs/plans/llm-judge.md` sets the bars; the tooling is:

**Hand labels** (`evals label RUN_ID --labeler aleena`). The screen shows the question, the
answer, each citation highlighted in its page, and asks "supported?"; then it reveals the gold
answer and asks "responsive?". Each label is tagged judge-dev or judge-test by a hash of the case
id, so the assignment is fixed before anyone sees a verdict and every attempt of a case lands on
one side. judge-dev is for tuning the prompt; judge-test is reported and never looked at while
tuning. Same discipline as the agent's dev/test split, one level up.

**Agreement** (`evals judge-validate RUN_ID`). For each verdict, with human and judge both
saying pass or fail per answer:

```
p_o   = share of answers where human and judge agree
p_e   = P(both say pass) + P(both say fail), from each rater's own pass rate
kappa = (p_o - p_e) / (1 - p_e)
```

Cohen's kappa is agreement beyond what two raters with those pass rates would reach by luck. A
judge that passes everything on a 90%-correct run agrees with the human 90% of the time and has
kappa 0, which is why plain agreement is the wrong number. The bar is kappa 0.7 on each verdict.
Alongside it, with the positive class being a real failure: **TPR** is the share of human-failed
answers the judge also fails (does it catch failures), and **TNR** the share of human-passed
answers it also passes (does it leave good answers alone). Both get Wilson intervals, and the
confusion counts are printed so nothing hides behind a ratio.

**Mutants and probes** (`evals judge-probe RUN_ID`). Agreement on a mostly-correct run is weak
evidence, so the judge is also attacked. From answers it passed on both verdicts, the tool
builds variants by deterministic text surgery:

| Variant | What changes | Judge must |
|---|---|---|
| number | the first standalone number (2026 to 2027, 5 to 6, 900 to 1800) | fail it |
| qualifier | the first "by default", "up to", "per Region" and so on is removed | fail it |
| citation | the first quote is swapped for an unrelated one from another answer | fail it |
| padding | a harmless closing sentence is appended | keep both verdicts |
| resample | nothing; judged again under a different cache salt | keep both verdicts |

Bars: at least 90% of mutants failed, at least 95% of probes unchanged, each with a Wilson
interval and n. Every miss is written to `results/judge-probes-<run>.json` with the judge's own
reasons, which is the input for the next prompt revision. The judge does not ship on a near
miss; the prompt changes and validation repeats, on judge-dev, with judge-test reported once.
